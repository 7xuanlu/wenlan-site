sustainable acquisition channel. This file freezes the native observations and
the repeated-release measurement contract so later work cannot relabel the wave
as website SEO or infer person-level attribution.

## Working hypothesis

A useful release, a directly installable Windows asset, and Mandarin
distribution on X or Threads may produce a repeatable GitHub discovery wave.
The current evidence aligns with that hypothesis, including the
Simplified-Chinese README traffic, but does not prove it. Google supplied only
`2` unique GitHub referrers and `wenlan.app` was not returned as a popular
GitHub referrer, so this wave is not recorded as an SEO result.

## Repeated-release protocol

Apply this protocol to the next two or three meaningful releases:

1. Freeze the pre-release GitHub star count and capture time.
2. Preserve the release publication time and each approved English, zh-TW, and
   zh-CN distribution time. Missing distribution remains `unavailable`; it is
   not filled with an estimate.
3. Read at 24 hours and seven days: stars, unique repository visitors, GitHub
   referrers, popular paths, and per-asset cumulative downloads.
4. Keep GSC and Vercel observations in their own native SEO and website lanes.
5. Record a wave as repeatable only when at least two later meaningful releases
   show a positive post-release star change with corroborating GitHub traffic or
   download observations. A flat or negative release remains a result, not a
   reason to rewrite the metric.

No social post, release publication, maintainer message, paid action, or other
external distribution is authorized by this measurement contract.
